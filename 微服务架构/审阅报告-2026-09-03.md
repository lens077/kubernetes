### H1「微服务设计」（L181–L239）

**问题**

1. L185 接口设计仍是 TODO。
2. L203「CQRS 模式，基于 Pull vs Push 模型」是错误定义。CQRS 是把写模型（命令）和读模型（查询）分离，与 Pull/Push 无关；后面对命令端 / 查询端的描述是对的，只是开头那句要删。
3. L213 有两处错误：
   - 「标准库的 fmt.Errorf 包含错误的行号，上下文等关键信息」：`fmt.Errorf` 不记录行号和调用栈，只做字符串拼接和 `%w` 包装。行号需要 `runtime.Caller` 或带栈的错误库。
   - 「正确的方法是记录日志并返回错误」：这是「错误处理两次」反模式，会导致同一错误在每一层都打一遍日志。通用原则是「内层用 `%w` 包装后返回，只在边界层（HTTP/RPC 中间件）记录一次」。文档后面的分层描述其实符合这个原则，只是这句总结自相矛盾。
4. 错误处理一节没有提 Go 1.20+ 的 `errors.Join`、多 `%w`，Go 1.21 的 `log/slog`，以及 Go 1.26 新增的 `errors.AsType`（[Go Weekly #589](https://golangweekly.com/issues/589)）。

**建议**

- 接口设计一节直接写你们的定稿：Protobuf + Buf（lint / breaking）+ Protovalidate 校验 + ConnectRPC；错误用 proto 定义的 reason 枚举映射到 Connect / gRPC status code。
- 拆分依据补「团队拓扑 / 康威定律」和「事件风暴」两种实践，并说明限界上下文与你们 TECH.md §5 的八个上下文对应。
- 错误处理改为：`data` 层包装原始错误 → `biz` 层翻译成领域错误 → 传输层映射状态码并记录一次，附 `trace_id`。

- 版本弃用补两个标准头：`Deprecation`（RFC 9745，2025-03 发布，值必须是日期 `@<unix秒>`，不能写 `true`，见 [RFC 9745 说明](https://datatracker.ietf.org/doc/draft-ietf-httpapi-deprecation-header/09)）和 `Sunset`（RFC 8594）。proto 层用 `option deprecated = true`。

- 数据库迁移补「扩展—收缩」（expand/contract）两步法，与「同时维护 v1/v2 至少 6 个月」呼应。
- 安全一节补：服务间只信任网关注入的头 + CiliumNetworkPolicy 只放行 Gateway → 服务；mTLS 按 TECH.md 的路线（先 Cilium WireGuard 节点加密，需要 workload mTLS 再评估 Istio Ambient）。

### H1「分布式事务」（L755–L1049）

这是需要重写的一章。

**问题**

1. L801「Transactional Outbox 事务收件箱」：Outbox 是「发件箱」；「收件箱（Inbox）」是消费者侧的去重表——正好是你们 `consistency.md` 里 `(consumer_group, event_id)` 唯一键那套。两个模式名都要用对。
2. L825「发送到消息队列后删除记录」：更稳妥的做法是记录 `published_at` 并保留一段时间，用于重放和对账；多 relay 并发要用 `FOR UPDATE SKIP LOCKED`，同一 `aggregate_id` 保序。你们的 relay 是在 broker `acks=all` 后才标记 `published`，与此一致。
3. L855–L859 混入「sql / 复制」按钮文字。
4. L899「canal」只支持 MySQL；你们是 PostgreSQL，现役是 Debezium（`components/kafka/README.md`），Debezium 还有 Outbox Event Router SMT，可以把「Outbox 表 + 日志追踪」合成一条链路。
5. L929–L1017「2PC MQ」有三处事实错误：
   - L977「发送确认消息失败：回滚」——此时本地事务已提交，无法回滚。正确机制是 MQ 对半消息做**事务回查**（RocketMQ 的 `checkLocalTransaction`），文档完全没提回查，而回查是这个模式成立的关键。
   - L1003「强一致性」——事务消息只保证「本地事务与消息投递最终一致」，消费者完成前两边状态不一致，是最终一致。
   - L1013「使用行级别的锁会导致在提交前都是没有被释放的」——事务消息不跨阶段持有数据库锁；持锁的是 XA / 数据库 2PC。
   - L1017「适用于强一致金融交易（跨行转账）」——跨行转账实际就是最终一致 + 对账，不是强一致。
   - 这个模式应直接点名 RocketMQ 事务消息；Kafka 的事务是生产端 exactly-once，没有半消息语义。
6. L1019 Seata：
   - 「解决了 2PC MQ 的行级锁问题」不准确。Seata AT 模式一阶段就提交本地事务、释放数据库锁，但全局锁在 TC 侧持有到二阶段；XA 模式则持有数据库锁。
   - Apache Seata 截至 2026-08 仍在孵化器，seata-go 最新 v2.1.0（2026-02-12，[Incubator 项目页](https://incubator.apache.org/clutch/seata.html)）。
   - 你们 `consistency.md` 明确「不引入 Seata（Java 生态，Go 栈不适配）」，集群里的 seata-server 属待下线残留。文档应改成「已评估，不采用」。
7. L1027–L1049 TCC 未写完：流程第 3 步为空，「空回滚」「防悬挂」只有标题，没写「幂等」。
8. **缺少 Saga**。这是微服务事务最常用的模式，也是你们的定稿：Order 内置 Saga Process Manager 同步编排 Checkout → 价格快照 → 库存预占 → 支付意图，失败自动逆向补偿；阶段性终态经 Outbox 发事件由下游编舞消费（`consistency.md` 2026-08-28 覆盖决议）。
9. 缺少「对账」：支付类场景的最终兜底是定时与支付渠道对账，而不是事务协议。

**建议**

重写为以下结构：

1. 问题定义：一个服务「改库 + 发事件」的原子性。
2. 可靠投递：Outbox（发件箱）→ relay（轮询 / CDC）→ broker ack 后标记；Inbox（收件箱）去重；DLQ 与告警阈值。
3. 跨服务流程：Saga 编排 vs 编舞，何时选哪个；补偿事件作为一等公民；超时兜底 job。
4. 需要同步反馈的段落：TCC 风格的预占/确认/释放（你们的 `ReserveGroup` / `ConfirmReservationGroup` / `ReleaseGroup`），写清空回滚、防悬挂、幂等三条。
5. 幂等：全局唯一 ID + 唯一约束 + 状态机；HTTP 侧可提 IETF `Idempotency-Key` 草案（尚未成 RFC）。
6. 外部平台回调（最大努力交付）：保留 L779–L797，补验签。
7. 对账：日切对账 + 差错处理流程。
8. 附录：2PC / XA、RocketMQ 事务消息、Seata、DTM、Temporal 各自适用范围，标注「本项目不采用」的原因。
