## LyraPass PG 崩溃循环修复（09:12，已恢复）
- **根因：containerd 2.3.4 默认 AppArmor profile 拒绝容器进程间 signal**。k1 节点 PG 进程标签 `cri-containerd.apparmor.d//&unconfined (enforce)`，内核 audit `operation="signal" ... signal=int ... peer="cri-containerd.apparmor.d//&unconfined" DENIED`，1h 内 signal=int 8437 次。PG crash recovery 末尾 `RequestCheckpoint()` 发 SIGINT 给 checkpointer 被 EPERM 拒（`could not signal for checkpoint: Permission denied`）→ 永久卡 `in crash recovery` → migrate 连不上 → cloud 0/2 → 维护任务「端点不可达」。自 11-15 起（lastSuccessful 停在 11-15 01:17），k1 03:06 重启只是重新暴露，非本次升级引入。
- **判障要点**：`kill -0 <pid>` 成功但 `kill -INT/-TERM <pid>` 全 `Permission denied` + CapEff=0 = AppArmor 信号过滤，不是 UID/数据/探针问题。放宽 liveness 仍卡 = 排除探针。查 `journalctl -k | grep apparmor.*DENIED`。

## AppArmor 信号豁免范围评估（10:00，结论：不扩大）
- 用户要求给"基础设施/数据库/缓存这类需要信号的"加 Unconfined 豁免。24h audit 实证：`signal=int`（真正阻塞 PG checkpoint）只有 `comm="postgres"` 8437 次，已由 LyraPass PG 修复覆盖；`signal=urg` 是 Go runtime 异步抢占、`ptrace read` 是 otelcol hostmetrics，均属无害降级。**没有第二个真正被信号阻塞的服务**，决定不扩大豁免。
- ⚠️ **CNPG 不能加 Unconfined**：`cs2-four` 命名空间有 `pod-security.kubernetes.io/enforce=restricted`，禁止 `appArmorProfile.type=Unconfined`，operator 报错循环（`violates PodSecurity "restricted:latest"`）。已回滚三个 Cluster CR（`pg-main`/`cs2four-pg`/`pal-pg`），期间计划内重启后全部恢复 healthy、0 重启。`pal-pg` 由 ArgoCD 跟踪（tracking-id），live patch 会被 selfHeal 覆盖。快照 k1 `/root/apparmor-signal-fix-20261125/`。
- 判据：只有多进程靠信号协调的服务（PostgreSQL）会因 AppArmor 信号拦截产生实际故障；Go/Java 单进程的 SIGURG/ptrace 拒绝是无害噪音；优雅停机 SIGTERM 由 kubelet 从外部发，不经容器 AppArmor。根治靠节点级 containerd profile 信号规则，根治前只对已证明故障的 Pod 豁免。
- 副作用：CNPG 重启期间 ArgoCD 缓存 palcommerce 空 health，hard refresh 无效，**重启 `sts/argocd-application-controller` 才恢复** 14 应用全 Healthy。
