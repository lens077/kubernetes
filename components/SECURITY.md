# 安全策略

## 支持范围

安全修复优先针对 `main` 分支当前维护的部署清单、脚本与文档。历史示例或已经标注为失效的方案可能不会继续维护，但发现的问题仍欢迎报告。

## 报告安全问题

不要在公开 Issue、Pull Request、提交信息或日志中披露以下内容：

- 密码、API Token、私钥、证书私钥、kubeconfig、云访问密钥。
- 可直接访问的集群地址、内部域名、未脱敏的资源清单或包含业务数据的日志。
- 可被立即利用的漏洞细节、复现步骤或受影响系统信息。

如 GitHub 已为本仓库启用私密漏洞报告，请通过仓库的 Security 页面创建私密报告。若该入口不可用，请通过维护者已公开的非公开联系方式报告，并在公开讨论中只说明“已私下报告”。

报告建议包含：

1. 受影响的文件路径、版本或提交。
2. 漏洞类型与影响范围。
3. 最小复现条件；其中所有环境信息和凭据必须脱敏。
4. 可行的缓解措施或修复建议（如有）。

## 凭据泄露处置

如果凭据已经进入 Git 历史或公开日志，立即将其视为失效并在源系统中轮换；仅删除工作区文件或提交一次“删除密码”的修复并不足以撤销泄露。随后清理受影响的配置、撤销权限，并评估是否需要重写历史或通知相关系统所有者。

## 安全配置原则

- 使用 Kubernetes Secret、环境变量或受管密钥系统保存敏感值，仓库只保留变量名和示例占位符。
- 生产入口默认使用受控的 Gateway、TLS 和最小权限 RBAC；不要因为示例方便而开放匿名管理接口。
- 使用节点本地卷、单副本服务或实验性 Chart 前，先评估节点故障、升级、备份和恢复路径。
